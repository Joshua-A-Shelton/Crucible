# Review 5: the UI library

The retained UI that both the editor and games are built with: elements
and layout, drawing, text, styling and themes, input and navigation, and
the controls. Decisions: ADRs 0019, 0020, 0057, 0059, 0060, 0061, 0062,
0063, 0065, 0124, 0127.

## What it does

A tree of C# elements is laid out, styled by a theme, drawn onto the
surface as one render step, and given the window's input. The editor is
built entirely from it; a game's menus and HUD use the same library with
their own theme.

```
 UIRoot (per surface)                                           GPU
 ────────────────────                                           ───
 element tree ─► measure / arrange ─► OnDraw(Canvas) ─► one    instanced
 (panels,         (only what changed)    (shapes, images,       draw, signed
  controls)                               text, clips)          distance shapes
      ▲ styles from a theme (.crstyle); input from UIInputSystem (pointer,
        keys, gamepad navigation); popups and tooltips in layers above
```

## How it works

### Elements, layout, and drawing (ADR 0019, 0059, 0060)

- **A retained tree of C# elements** (`UIElement`). Panels arrange
  children: `StackPanel`, `Grid` (Auto, Pixels, or Star sizes), `DockPanel`,
  `AnchorPanel`; games add their own in C#.
- **Measure, then arrange,** only for what changed: a change marks its
  path to the root dirty.
- **Any element can draw itself** by overriding `OnDraw(Canvas)`: filled
  and stroked rectangles with rounded corners, images, nine-slices, text,
  lines, shadows, clips, transforms. The editor's viewports, the palette,
  and the graphs are such elements.
- **One render step per root:** everything becomes instances of one
  shader, usually one draw for the whole UI, shapes as signed distance
  fields so edges are smooth at any scale. Redrawn only when something
  changed.
- **DPI:** layout is in logical units, scaled to the monitor, and every
  element's rectangle snaps to whole pixels.

### Text (ADR 0020, 0057, 0065)

- **HarfBuzz shapes, FreeType rasterizes** into glyph atlases at the exact
  size (sharp at small sizes), or as distance fields for text that's
  scaled or animated. UTF-8 everywhere; Latin scripts in v1, with shaping
  behind an interface so other scripts can come.
- **Text editing** (`TextField`, `NumberField`): selection, undo, the
  clipboard, typed text from the platform's text input (page 2).

### Styling and animation (ADR 0061, 0124)

- **Styled properties** (background, padding, font size, …) take their
  value from layers: an animation, a value set in code, the best-matching
  style, the default.
- **Selectors are a type, classes, and states** (`Button.primary:hover`);
  the more specific wins. **No parent or descendant parts.**
- **Themes are `.crstyle` JSON assets** (or built in code); changing one
  restyles everything using it. The editor's look and a game's are just
  different themes.
- **Animation:** style transitions and tweens, on real time, so menus
  animate over a paused game.

### Input (ADR 0062, 0124)

- **Events bubble** from the element under the pointer up through its
  parents until one handles them; roots report what they used, so a game
  ignores input the UI took.
- **Keyboard and gamepad navigation:** unhandled arrows and the D-pad move
  focus spatially; South activates, East cancels; focus scopes trap focus
  in dialogs and menus.
- **Popups** (menus, drop-downs, dialogs) and **tooltips** draw in layers
  above the content.

### Controls (ADR 0063, 0124, 0127)

- Buttons, toggles, sliders, number and text fields, combo boxes, list
  boxes (virtualized: only visible rows exist), tree views, menus (which
  scroll when they don't fit), dialogs, color pickers, icons. Controls'
  parts are typed child elements, styled like any element.

## Why it was built this way

- **Retained, with custom drawing:** retained trees make layout, focus,
  and docking work for free; custom drawing covers the tools that don't
  fit (timelines, graphs, viewports).
- **C# logic, native text:** UI code iterates fast in C# and hot reloads;
  shaping and rasterizing are where native speed matters.
- **One draw, distance fields:** cheap on the GPU and crisp at any scale.
- **A small selector set:** predictable styling, no cascade to debug.
- **Gamepad navigation built in,** because games are played with
  controllers, Steam Deck first.

## What I'd question

1. **No descendant selectors costs workarounds.** An icon can't follow its
   button's hover, a tooltip's label needed its own class, disabled play
   buttons dim by opacity instead of color (all in step 7c). A small
   "child of" or "inside" selector would cover them.
2. **Layouts are code only.** Themes are assets, but a screen's layout
   (a game's HUD, its menus) is built in C#. A designer can restyle it but
   can't arrange it; a layout asset (and later an editor for it) would let
   them.
3. **No data binding.** Controls are filled and read by hand each frame or
   on events; an inventory list or a stat panel is all wiring. A light
   binding (a property path, or an observable value) would cut that down.
4. **Latin text only.** The anime-esque reference games suggest Japanese
   might be wanted (titles, names, a localized release); CJK needs font
   fallback and larger glyph caches, and shaping is already ready for it.
5. **Composition bugs found late.** Making menus scroll found a scroll bar
   crash and items finding their menu by position in the tree; Add
   Component's dialog found a name-splitting bug. The controls' tests
   cover each control alone; combinations (a menu in a scroll view, a
   list in a dialog) are where bugs were.
